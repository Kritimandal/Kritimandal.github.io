PHP Student API: a plain PHP service with the rules in the database

A REST API for student records without a framework. It started as a set of separate PHP scripts and was rebuilt with one entry point, prepared statements throughout, and search, reports and change history in MySQL.

My part
All of it: API, schema, routines, tests, CI
Language
PHP 8.1 with PDO, no framework
Database
MySQL 8 or MariaDB 10.4+: stored procedures and triggers
Links
Source on GitHub

01Starting point

The first version was a set of separate PHP scripts. The rebuild had three goals: make every query safe from SQL injection, make every endpoint behave the same way, and make it testable against a real database.

The result has a single entry point and a small router, one repository class that holds all the SQL, a validator, and JSON responses with consistent status codes: 200, 201, 204, 400, 404, 405, 422 and 500.

02Decisions

  1. Prepared statements everywhere, with native prepares.

    Every query uses PDO prepared statements or a stored procedure with bound parameters, and emulated prepares are off.

  2. Escape % and _ in search terms.

    Bound parameters stop injection but not LIKE wildcards, so a search for 50% would otherwise match everything. They are escaped before the search procedure runs.

  3. Record history with triggers.

    Insert, update and delete triggers write the old and new values to an audit table. The history is kept in the database itself and stays available after a student is deleted.

  4. Put search and reports in stored procedures.

    Search with city filter and pagination, the count for pagination, the per-city report and the history lookup are each one procedure.

  5. All-or-nothing bulk insert.

    Up to 100 students can be created in one request, inside a transaction: if one row is invalid, none are saved.

  6. Strict input.

    Unknown fields are rejected, age must be a real integer rather than the string "20", and routes only match positive whole numbers, so /students/1 OR 1=1 is a 404.

  7. Do not leak database errors.

    Unexpected errors are logged and the client gets a general 500 message.

03Code

The update trigger, from database/routines/trg_students_after_update.sql:

CREATE TRIGGER trg_students_after_update
AFTER UPDATE ON students
FOR EACH ROW
INSERT INTO student_audit (student_id, action, old_data, new_data)
VALUES (
    NEW.id,
    'update',
    JSON_OBJECT('name', OLD.name, 'age', OLD.age, 'city', OLD.city),
    JSON_OBJECT('name', NEW.name, 'age', NEW.age, 'city', NEW.city)
)

The per-city report is a single procedure:

CREATE PROCEDURE sp_city_summary()
BEGIN
    SELECT
        city,
        COUNT(*) AS students,
        ROUND(AVG(age), 1) AS average_age,
        MIN(age) AS youngest,
        MAX(age) AS oldest
    FROM students
    GROUP BY city
    ORDER BY students DESC, city;
END

bin/migrate.php creates the tables and then recreates every trigger and procedure, so it is safe to run again after a change.

04A bug CI found

The tests passed on my local MariaDB but failed in GitHub Actions on MySQL 8 with an "illegal mix of collations" error in the search procedures. The procedure parameters were taking the database's default character set, which did not match the table columns on MySQL 8.

The fix was to declare the parameters as utf8mb4 explicitly, so search behaves the same whatever the database default is:

IN p_term VARCHAR(100) CHARACTER SET utf8mb4,
IN p_city VARCHAR(100) CHARACTER SET utf8mb4

It was the CI run against MySQL 8, not my local database, that caught it.

05Tests

33 tests. Unit tests cover validation, routing and JSON parsing. Integration tests call the API against a real database and cover the stored procedures, the triggers, the bulk transaction, SQL injection attempts and error responses. GitHub Actions runs them all against MySQL 8 on every push.
